# Caddy 反代「规则 - 子规则」两层模型设计方案

> **版本**：v1.0（设计稿，未实施）
> **日期**：2026-10-31
> **作者**：Deva（模型 `gitllc:gemini-4-argon`）
> **状态**：待评审
> **目标**：把当前扁平的单域名站点结构，重构为对齐 Lucky 的两层模型（端口规则 + 域名子规则）

---

## 一、背景与问题

### 1.1 当前实现

Caddyfile 采用「每个域名一个独立站点块」的扁平结构：

```caddyfile
{
    https_port 8886
    auto_https disable_redirects
    servers { protocols h1 }
}

orca6.king.nyc.mn {
    bind ::
    tls /etc/caddy/ssl/wildcard.crt /etc/caddy/ssl/wildcard.key
    reverse_proxy localhost:6768
}

caddy.king.nyc.mn {
    bind ::
    tls /etc/caddy/ssl/wildcard.crt /etc/caddy/ssl/wildcard.key
    reverse_proxy localhost:3100
}
```

MCP Server 通过 `lib/caddy.js` 提供增删改查，操作方式为「读取整份 Caddyfile 文本 → 追加/删除文本块 → validate → reload」。

### 1.2 无法表达的四个能力

| 需求 | 现状 | 说明 |
|---|---|---|
| 一个端口下挂多条域名规则 | ❌ | 语法上只能每域名一个站点块，端口在全局写死 |
| 每条规则独立 TLS 开关 | ❌ | `https_port` 是全局设置 |
| 多后端负载均衡 | ❌ | 无数据结构与 UI 支持 |
| 每规则独立 Basic Auth / IP 过滤 / UA 过滤 / 日志 | ❌ | 完全没有 |
| 规则整体启用/禁用 | ❌ | 只能删掉再重写 |

### 1.3 对标对象：Lucky 的两层模型

Lucky 的配置结构（源码 `module/reverseproxy/conf/reverseproxy.go`）：

```
ReverseProxyRule（Web 服务规则）
├── ListenIP / ListenPort        监听地址
├── EnableTLS                    是否启用 TLS
├── Network                      tcp / udp
└── ProxyList[]                  ← 子规则
    ├── Domains[]                前端域名（可多个）
    ├── Locations[]              后端地址（多后端即负载均衡）
    ├── EnableAccessLog          独立日志开关
    ├── LogLevel / AccessLogMaxNum
    ├── EnableBasicAuth          独立 Basic 认证
    ├── BasicAuthUser / Passwd
    ├── SafeIPMode               IP 黑白名单
    ├── SafeUserAgentMode        UA 黑白名单
    ├── UserAgentfilter
    ├── AddRemoteIPToHeader      注入真实 IP 头
    ├── AddRemoteIPHeaderKey
    └── CustomRobotTxt / RobotTxt
```

**核心特点**：一个监听端口下挂多条子规则，按域名分流，每条子规则策略独立。

## 二、目标数据模型

### 2.1 唯一真相源：`/etc/caddy-mcp/sites.json`

```json
{
  "version": 1,
  "servers": [
    {
      "id": "srv_8886",
      "listen": ":8886",
      "port": 8886,
      "enableTLS": true,
      "tlsCert": "/etc/caddy/ssl/wildcard.crt",
      "tlsKey": "/etc/caddy/ssl/wildcard.key",
      "httpProtocols": ["h1"],
      "enabled": true,
      "rules": [
        {
          "id": "rule_orca6",
          "domains": ["orca6.king.nyc.mn"],
          "upstreams": ["localhost:6768"],
          "lbPolicy": "",
          "timeouts": { "read": "24h", "write": "24h" },
          "accessLog": {
            "enabled": true,
            "file": "/var/log/caddy/orca6.log",
            "level": "INFO"
          },
          "basicAuth": null,
          "ipFilter": { "mode": "none", "list": [] },
          "uaFilter": { "mode": "none", "list": [] },
          "realIP": { "enabled": true, "header": "X-Real-IP" },
          "remark": "Orca Agent 服务",
          "enabled": true
        },
        {
          "id": "rule_caddy",
          "domains": ["caddy.king.nyc.mn"],
          "upstreams": ["localhost:3100"],
          "lbPolicy": "",
          "timeouts": { "read": "300s", "write": "300s" },
          "accessLog": {
            "enabled": true,
            "file": "/var/log/caddy/mcp-access.log",
            "level": "INFO"
          },
          "basicAuth": null,
          "ipFilter": { "mode": "none", "list": [] },
          "uaFilter": { "mode": "none", "list": [] },
          "realIP": { "enabled": true, "header": "X-Real-IP" },
          "remark": "MCP 控制台",
          "enabled": true
        }
      ]
    }
  ]
}
```

### 2.2 字段说明

**Server（端口规则）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✅ | 唯一标识，`srv_` 前缀 |
| `listen` | string | ✅ | 监听地址，如 `:8886` |
| `port` | number | ✅ | 端口号（便于全局 `https_port` 生成） |
| `enableTLS` | boolean | ✅ | 是否启用 TLS |
| `tlsCert` / `tlsKey` | string | 条件 | `enableTLS=true` 时必填 |
| `httpProtocols` | string[] | ✅ | `["h1"]` / `["h1","h2"]` |
| `enabled` | boolean | ✅ | 整条规则启停 |
| `rules` | array | ✅ | 子规则列表 |

**Rule（子规则）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✅ | 唯一标识，`rule_` 前缀 |
| `domains` | string[] | ✅ | 前端域名，可多个 |
| `upstreams` | string[] | ✅ | 后端地址，多后端需配 `lbPolicy` |
| `lbPolicy` | string | 条件 | `round_robin` / `random` / `least_conn` |
| `timeouts` | object | ✅ | `{read, write}`，Caddy duration 格式 |
| `accessLog` | object | ✅ | `{enabled, file, level}` |
| `basicAuth` | object\|null | ✅ | `{user, hash}`（hash 为 bcrypt） |
| `ipFilter` | object | ✅ | `{mode: none/whitelist/blacklist, list[]}` |
| `uaFilter` | object | ✅ | `{mode: none/blacklist, list[]}` |
| `realIP` | object | ✅ | `{enabled, header}` |
| `remark` | string | ❌ | 备注 |
| `enabled` | boolean | ✅ | 单条启停 |

## 三、生成产物

`lib/generator.js` 把 `sites.json` 渲染为 `/etc/caddy/Caddyfile`：

```caddyfile
{
    https_port 8886
    auto_https disable_redirects
    admin localhost:2019
    servers {
        protocols h1
    }
}

:8886 {
    bind ::
    tls /etc/caddy/ssl/wildcard.crt /etc/caddy/ssl/wildcard.key

    # ── rule_orca6 ── Orca Agent 服务
    @rule_orca6 host orca6.king.nyc.mn
    handle @rule_orca6 {
        reverse_proxy localhost:6768 {
            transport http {
                read_timeout 24h
                write_timeout 24h
            }
            header_up X-Real-IP {remote_host}
            header_up X-Forwarded-For {remote_host}
        }
        log {
            output file /var/log/caddy/orca6.log
            level INFO
        }
    }

    # ── rule_caddy ── MCP 控制台
    @rule_caddy host caddy.king.nyc.mn
    handle @rule_caddy {
        reverse_proxy localhost:3100 {
            transport http {
                read_timeout 300s
                write_timeout 300s
            }
            header_up X-Real-IP {remote_host}
            header_up X-Forwarded-For {remote_host}
        }
        log {
            output file /var/log/caddy/mcp-access.log
            level INFO
        }
    }
}
```

### 高级功能对应的 Caddy 语法

**Basic Auth**
```caddyfile
basic_auth {
    admin $2a$14$<bcrypt-hash>
}
```

**IP 黑名单**
```caddyfile
@rule_x_blocked not remote_ip 192.168.20.0/24 10.0.0.0/8
respond @rule_x_blocked "Forbidden" 403
```

**IP 白名单**
```caddyfile
@rule_x_allowed remote_ip 192.168.20.0/24
@rule_x_blocked not remote_ip 192.168.20.0/24
respond @rule_x_blocked "Forbidden" 403
```

**UA 过滤**
```caddyfile
@rule_x_ua header_regexp User-Agent (?i)(bot|crawler|spider)
respond @rule_x_ua "Forbidden" 403
```

**多后端负载均衡**
```caddyfile
reverse_proxy 192.168.20.180:8080 192.168.20.180:8081 {
    lb_policy round_robin
}
```

## 四、核心组件

### 4.1 `lib/generator.js`（纯函数，JSON → Caddyfile）

```javascript
export function render(sites) { /* 见正文 */ }
function renderRule(rule) { /* 见正文 */ }
```

**设计要点**：
- 纯函数，无副作用，可单测
- 输出确定性：同样输入必得同样输出（便于 diff 与版本控制）
- 不使用时间戳等易变内容（注释里用 `rule.id` 而非当前时间）

### 4.2 `lib/validator.js`（三层校验）

| 层级 | 检查内容 |
|---|---|
| **L1 结构** | `servers` 是数组、必填字段存在、类型正确 |
| **L2 语义** | 端口唯一、域名全局唯一、TLS 启用必须有证书、多后端必须有 LB 策略 |
| **L3 格式** | 域名符合 RFC、上游符合 `host:port`、超时符合 Caddy duration、bcrypt hash 前缀正确 |

**校验失败一律拒绝写入，不做部分应用。**

### 4.3 `lib/apply.js`（原子应用，最关键）

```
1. validateSites(sites)         → 失败即抛错，不碰文件
2. render(sites)                → 生成新 Caddyfile 文本
3. copyFile(Caddyfile, bak)     → 备份
4. writeFile(Caddyfile, new)    → 写入
5. caddy validate               → 失败 → 回滚 → 抛错
6. systemctl reload caddy       → 失败 → 回滚 → 抛错
7. writeFile(sites.json)        → 只有全部成功才保存 JSON
```

**关键设计**：
- **JSON 是唯一真相源**，Caddyfile 是生成产物
- **JSON 最后写入**：避免出现「JSON 已更新但 Caddyfile 未生效」的不一致状态
- **任一步失败全回滚**：用 `copyFile(bak, Caddyfile)` 恢复

### 4.4 `lib/migrate.js`（一次性迁移脚本）

从当前 Caddyfile 手工提取两条规则，生成初始 `sites.json`，然后 apply 一次，验证生成的 Caddyfile 与原来功能等价。

## 六、实施步骤与验收标准

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| **1** | `lib/generator.js` | 用现有两条规则生成，与手工 Caddyfile 功能等价（`caddy validate` 通过，两个域名访问正常） |

## 七、风险与回滚

| 风险 | 缓解措施 |
|---|---|
| 生成的 Caddyfile 有语法错误 | `apply.js` 内置 validate，失败自动回滚 |
| reload 后服务不可用 | 保留最近 10 个备份，一条命令恢复 |
| JSON 与 Caddyfile 不一致 | JSON 最后写入；提供 `caddy_config_validate` 对比检查 |
| 迁移过程服务中断 | 迁移在业务低峰执行；reload 是平滑的（不断连接） |
| 多端口配置冲突 | validator 强制端口唯一 |

**回滚命令**（任何时刻可用）：
```bash
cp /etc/caddy/Caddyfile.bak.<timestamp> /etc/caddy/Caddyfile
systemctl reload caddy
```

## 八、需要评审确认的四个决策点

### 决策 1：高级功能的优先级

- **A（推荐）**：先做核心（端口 + 域名 + 后端 + 日志 + 启停），Basic Auth / IP / UA 过滤作为第二阶段
- **B**：一次做全

**推荐 A 的理由**：核心功能覆盖 90% 场景，先上线先验证，高级功能后续增量加不影响架构。

### 决策 2：多后端负载均衡

- **A**：要（实现 `lb_policy`，支持 round_robin / random / least_conn）
- **B**：不要（只支持单后端，简化实现）

**待确认**：Lucky 的 `Locations[]` 多后端能力，实际使用频率如何？若从未用过可先砍掉。

### 决策 3：日志策略

- **A**：每条子规则独立日志文件（对齐 Lucky，便于按站点排查）
- **B**：全局一份，按域名区分（省文件句柄，查询需过滤）

**推荐 A**：与 Lucky 一致，符合用户预期；文件数不多时可接受。

### 决策 4：是否支持多端口规则

- **A**：支持多个 `servers`（完整两层模型，将来可加 `:8887` 等）
- **B**：单端口（`servers` 数组只放一个，简化实现与 UI）

**推荐 A**：数据结构上支持多端口几乎不增加复杂度，但保留了扩展性。

## 十、架构位置说明（重要）

理解这套方案在整体架构中的位置，对评估风险很重要：

```
公网
  ↓
路由器 192.168.20.1（公网 IPv6 ...::1）
  ├── Lucky 反代（80/443）← 所有 *.king.nyc.mn 的公网入口
  │   ├── vcs.king.nyc.mn  → vps-commander Hub
  │   ├── msg.king.nyc.mn  → 消息服务
  │   └── 其他服务
  └── DNAT
      └── orca6 / caddy → 服务器 wjy5010u（...::c6c）:8886
```

**本方案改造的是服务器 wjy5010u 上的 Caddy**，只承载 `orca6` 和 `caddy` 两个子域名。

**动它不会影响路由器和 Lucky，因此不会波及全舰队。** 这是本方案可以在生产环境相对安全推进的前提。

⚠️ **但若将来把 Caddy 装到路由器、替换 Lucky，则属于高风险变更**——那一步需要单独的灰度与回滚方案，不在本设计范围内。

## 附录 C：评审意见（追加）

> 评审方：Claude（应用于 orca 工作区的评审）
> 说明：以下意见基于第一至第八章的内容。第四章 4.1（generator）的细节未完整核对，相关结论以已读内容为准。

### C.1 必须修正（实施前）

**C.1.1 客户端真实 IP 获取有误（高）**

设计中 `header_up X-Real-IP {remote_host}` 取的是 Caddy 直接看到的对端地址。按第十章的链路（公网 → 路由器 DNAT → Caddy），`remote_host` 拿到的是上游侧地址，不是真实客户端。因此：
- 第二章中的 `ipFilter` 会按上游地址匹配，黑白名单失效或误伤；
- 访问日志中的客户端 IP 全部相同。

修正方向：
- 在全局配置中设置 `trusted_proxies`，只信任路由器或 Lucky 的地址；
- 使用 `client_ip` 获取真实来源，而不是直接取 `remote_host`；
- `X-Real-IP` 只能在可信代理下采信。否则任何公网客户端都能伪造该头，绕过 IP 过滤。

**C.1.2 apply.js 的写入顺序应调整（中）**

当前第四章 4.3 的流程先写入正式的 `/etc/caddy/Caddyfile`，再校验，失败后回滚。建议改为：
1. 生成内容写入临时文件，用 `caddy validate --config <tmp>` 校验；
2. 校验通过后原子替换（`rename`）正式文件，再 reload；
3. 整个过程加 `flock`，防止两个 MCP 调用并发写入。

这样校验失败时正式文件从未被改动，回滚逻辑也更简单。

**C.1.3 admin API 的暴露面未说明（中）**

生成器输出了 `admin localhost:2019`，文档没有说明它是否被 MCP 使用，以及是否允许其他本地进程访问。请明确：关闭 admin API，或只允许本地并由 MCP 独占使用，并写入文档。

### C.2 对第八章四个决策点的建议

| 决策 | 文档推荐 | 评审建议 |

| 1. 功能范围 | A（核心先上线） | 同意。`ipFilter` 依赖 C.1.1 的修正，放到第二阶段，修正后再上线 |
